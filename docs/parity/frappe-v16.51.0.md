# Frappe v16.51.0 parity specification

Reference: [`v16.51.0`](https://github.com/frappe/frappe/releases/tag/v16.51.0), commit [`6b450a166e076dd842e4db7ea0843f62881e62ac`](https://github.com/frappe/frappe/tree/6b450a166e076dd842e4db7ea0843f62881e62ac). Baseline stays fixed until an explicit update.

## Coverage and evidence

This working specification has **116 capability requirements**, **44 field types**, and **301 canonical standard DocType definition paths**. The repository tree is complete (`truncated=false`). Two nested email-notification template JSON files are not standard DocType definitions and are excluded from the canonical count.

This is a comprehensive planning baseline with per-feature positive/negative acceptance criteria. It is not a certified exhaustive behavioral catalog: source review is selective. The assistant trial baseline and harness were removed for user-led learning; no runtime fixtures are currently retained. Behavioral/document/permission/browser comparisons remain pending. Individual DocType definitions/controllers, optional configuration behavior, and incidental legacy edge cases require the prescribed reference audit before parity can be certified.

Machine-readable [features](features.json), [CSV checklist](features.csv), [field types](field-types.csv), and [standard DocTypes](standard-doctypes.csv) are authoritative inventories. Every feature carries a source, owner, milestone, proposed test ID, evidence state and implementation state. A source-path inventory confirms existence, not implemented semantics.

## Compatibility contract

- Behavioral parity: document actions, permissions, metadata, flows, reports and platform operations.
- User-experience parity: pinned screens/workflows, navigation, field interactions, loading/errors and supported responsive behavior. Exact screenshot tolerances are fixed when reference fixtures are captured.
- REST compatibility: explicit v1/v2/RPC contracts with endpoint-specific serializers and tests.
- Client SDK compatibility: a tracked public scripting facade, not universal jQuery/DOM compatibility.
- TypeScript app SDK: semantic equivalent of server-side document/app extension capabilities.

Explicit implementation differences: TypeScript replaces Python app/server scripts; PostgreSQL is the native database; React replaces browser internals; Nunjucks/Chromium replace template/print internals; BullMQ replaces queue internals. None imply that existing Python apps, Jinja templates, raw SQL reports, or site files can be imported unchanged. Migration/import adapters are separate requirements where portability is needed.

Security fixes must not be reverted merely to reproduce unsafe exposure. Track safe payload differences as deliberate divergences. Do not declare a feature complete while silently omitting its difficult subfeatures.

## Requirement lifecycle

`not_started` → `in_progress` → `implemented` → `verified`.

`verified` requires reference fixture, passing positive/negative/failure comparisons, relevant cross-site/concurrency/upgrade tests, and no unexplained differences. `approved_divergence` must link an ADR and remain visibly separate from exact parity. Optional integrations are exercised in a configured reference environment; unconfigured does not mean out of scope.

## Reference capture protocol

Run exactly the pinned Frappe source in an isolated environment with recorded app/config/runtime versions. Create two sites, actors with contrasting roles, normal/child/single/tree/submittable models and fixed seed data. Store normalized request/response, lifecycle trace, database outcomes, events, and fixed-viewport screenshots. Remove credentials/private content and only normalize nondeterministic identifiers/timestamps. Do not normalize away business differences.

Live documentation describes intent; tagged code and reproducible behavior settle release-specific details. Each feature must expand its behavior cases before implementation; a high-level positive criterion alone is not enough to certify every method.

## Capability checklist

The owner is a responsibility, not a mandated premature package split. Milestones express dependencies; every row remains in final scope.

## Definition-level coverage

For every standard DocType inventory entry, audit its actual JSON definition, controller, tests, form/list code and installation/fixture role. Record parent/child/single mode, fields and options, permissions, naming, events, business actions, endpoint links, customization precedence and upgrade behavior. Helper child definitions are required even when they have no standalone UI.

For every field type, compare storage/normalization, inputs, formatting, validation, filters, permissions, import/export, printing, empty/null/default handling and supported dependency expressions. Layout-only types must be tested as layout, not forced into stored columns.

## Final certification gate

All capability, field, standard-DocType and public-API inventories are audited; baseline tests pass; differences are listed; configured connectors are tested; reference UI evidence exists; installed-app upgrade/customization tests pass; real data restore succeeds; workload assumptions and operational limits are measured. Until then, describe the system as a rebuild in progress rather than a 1:1-compatible completed framework.
